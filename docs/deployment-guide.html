ServiceNow  ×  Nutrient Web SDK  ·  Deployment Runbook

In‑platform PDF viewing & digital signing for ServiceNow

Embed the Nutrient Web SDK inside ServiceNow so users can open, annotate, convert, and digitally sign record attachments — without the file ever leaving the platform. This runbook takes a ServiceNow admin from empty instance to a working, validated build.

Scope  Global UI  Classic (Next Experience list/form) Artifacts  5 Signing  Nutrient DWS (AATL) Est. time  45–60 min

The solution is five Global‑scope artifacts working together. An attachment click is intercepted and the file opens full‑screen in the Nutrient Web SDK; signing is brokered server‑side through the Nutrient DWS API so no API keys reach the browser.

Server scripts need ECMAScript 2021 mode

Artifacts 1 and 2 use modern JavaScript (const/let, template literals, arrow functions). Turn on “ECMAScript 2021 mode” on the Script Include and the Scripted REST resource. If token generation returns HTTP 500 after deploy, this toggle is the first thing to check.

Client script must not be sandboxed

On nutrient_hook, uncheck “Isolate script.” Isolated client scripts get a stripped context with no real DOM, so the attachment interceptor can't attach its listener (symptom: Cannot read properties of null (reading 'addEventListener')). Also set property glide.script.block.client.globals = false.

No certificate‑table access needed

Trusted certificates are loaded server‑side by the Script Include (getTrustedCertificates), so end users never need read access to sys_certificate. This is intentional — keep it that way.

04

Trusted certificates

For signatures to validate valid instead of warning, upload the DWS signing CA chain. Go to All → System Definition → Certificates and create three separate records — one per certificate, each Format PEM, Active ✓. Paste one certificate per record (never combine them into one field).

#Certificate (CN)Role in chain
1GlobalSign Atlas R45 AATL CA 2020Intermediate
2GlobalSign R45 AATL Root CA 2020Intermediate
3GlobalSign Document Signing Root R45Root anchor (self‑signed)

These chain the DWS signer up to a publicly‑trusted, Adobe‑Approved‑Trust‑List root — the resulting signatures are genuinely valid, not self‑signed.

!

Known limitations & gotchas

Classic UI only — not Workspace

The integration relies on a client script + DOM interception, which run in the classic platform UI. Inside Agent / Service Operations Workspace the hook does not run, and attachment clicks use ServiceNow's native viewer. Supporting the Workspace is a separate, workspace‑native build.

Sign, then Save, breaks the signature

Save re‑exports and re‑uploads the PDF, which rewrites the bytes and invalidates any existing signature (validates as status: 'error' / “tampered”). Treat signing and convert‑on‑save as mutually exclusive per document, or extend Save to preserve signed bytes.

UI Page is Jelly — no ${…} template literals

ServiceNow UI Pages are Jelly templates and evaluate ${…} server‑side, blanking any JavaScript template‑literal interpolation before it reaches the browser. In the UI Page HTML and Client script use string concatenation. const/let/arrow functions are safe. (This does not apply to the Script Include, Scripted REST API, or client script hook.)

Evaluation license

An evaluation Web SDK license renders cleanly (no watermark) but logs an “evaluation license” note. Swap in a full production license before go‑live.
